# CLAUDE.md

Guidance specific to the jigsaw-puzzle feature (see the root `CLAUDE.md` for repo-wide conventions).

## Phase 6: Jigsaw Puzzle Minigame

An image-reassembly puzzle that stands in for a flat investigation/perception-style skill check. The GM sends a request into chat for a specific PC, DC, skill, and circumstance modifier (`pf2eCustomizations.requestJigsawPuzzle()`), plus an image source choice (random from a pool, or a specific pinned image); any owning player can open the puzzle from the chat card (one attempt in flight at a time). A random (or GM-pinned) image is sliced into a grid of rectangular tiles, scrambled into a tray, and generated fresh per attempt; grid size is derived from the DC alone (no secondary "clue completeness" axis, deliberately dropped for v1 — see `design.md`).

- **Target files**: `scripts/features/jigsaw-puzzle/` (`jigsaw-puzzle-logic.js`, `jigsaw-puzzle-app.js` + `.hbs`, `jigsaw-puzzle-chat.js` + `-chat-card.hbs`), `scripts/macros/request-jigsaw-puzzle.js`, `assets/features/jigsaw-puzzle/*` (bundled placeholder images).
- **Fifth `ApplicationV2` + `HandlebarsApplicationMixin` feature**, and the **first feature in this codebase to load/manipulate an image at all** — no canvas, no PIXI, plain CSS `background-position` slicing on `<button>` tiles instead (true interlocking jigsaw tab/blank shapes were considered and rejected — no SVG/canvas precedent anywhere else in this module).
- **Layout is a scrambled tray + fixed empty grid slots**, not free-drag-anywhere-on-canvas. A tile can be dropped into any slot, right or wrong — no snap-back, no mistake counter, no per-cell correctness indicator (`.is-filled` only ever means "occupied," never "correct"). The player has to eyeball mismatches against the rest of the picture and re-drag them.
- **Both native HTML5 drag-and-drop and a click-select-then-click-place fallback work on the exact same elements** (tray tiles and grid slots are both real `<button>`, both `draggable="true"` where applicable and both wired to the same `data-action="tileClick"`) — a combination no other feature in this codebase has attempted (timeline-puzzle's draggable blocks and its ◀/▶ button fallback are deliberately separate elements). If real browser testing surfaces a click/drag conflict on the same element, the documented fallback is splitting them into a wrapper `<div draggable>` containing an inner `<button data-action>`.
- **Time allowance formula includes a piece-count term**, a deliberate deviation from every sibling feature (where only `totalPcStat` drives time and DC only drives content volume): `baseTimeAllowanceSeconds = totalPcStat * PER_STAT_POINT + pieceCount * PER_PIECE_SECONDS + BASE_SECONDS`. Justified because manipulation effort scales close to linearly with piece count here, unlike reading a fact pool or filling a fixed-size grid. See `design.md` for the worked examples and first-draft constants (expect a retuning pass, same as every sibling needed).
- **Outcome-on-expiration boundary is the OPPOSITE direction from fact-sifter's own ratio check**: here, `correctSlotCount / pieceCount >= 0.5` is a plain **failure**; `< 0.5` is **criticalFailure**. Fact-sifter's equivalent check lands exactly 50% in criticalFailure. This is intentional per this feature's own locked spec — do not "fix" it to match fact-sifter.
- **Image source is three-layered**: a bundled default folder (`assets/features/jigsaw-puzzle/`), an optional GM-configured custom folder (`jigsawPuzzleCustomImageFolder` world setting, using Foundry's native `filePicker: 'folder'` setting config — no manual FilePicker wiring needed for that one), and a per-request GM override to pin one specific image (via a native `<file-picker type="image">` custom element in the request Dialog — the first use of that element in this codebase, read via direct `.value` access rather than trusted `FormData` pickup, since its form-association inside a bare `Dialog` form hasn't been exercised here before). A `jigsawPuzzleIncludeBundledWithCustom` world setting controls whether the bundled folder stays in the random pool once a custom folder is set.
- **No secondary clue-completeness axis** (`neededRoll`/`clueMode`) for v1 — a "ghost overlay" reference-image concept was seriously considered (a natural analog to a jigsaw box lid) and explicitly deferred, not forgotten. Revisit if playtesting shows the puzzle needs more mechanical depth at high DC.
- **Trigger**: same pattern as the other four features — `Hooks.on('renderChatMessageHTML', ...)` renders/gates an "Attempt Puzzle" button based on `flags['pf2e-customizations'].jigsawPuzzle` (claim/resolution state on the actor, immutable raw GM inputs on the message).
- **Image resolution happens at GM request time, not per-attempt** — a real, confirmed bug: `FilePicker.browse` (needed to list candidate images) requires the "Use File Browser" permission, which defaults to GM-only in most worlds' permission config. The first draft resolved the pool inside `onAttempt()` (run by whichever player clicked Attempt), and every non-GM player got "No puzzle images are available" even with a populated bundled folder. Fixed by resolving `imagePath` and preloading it for `aspectRatio` once in `request-jigsaw-puzzle.js` (always GM-run), storing both directly on the `ChatMessage` flag. `onAttempt()` is now fully synchronous again, same shape as every sibling feature — the trade-off is the chosen image no longer varies across re-attempts of the same request (grid layout and tray shuffle still do).
- **Aspect ratio is locked to the source image's own natural proportions**, resolved once via the request-time preload (`naturalWidth`/`naturalHeight` → `aspectRatio = "${w} / ${h}"`), applied as an inline `aspect-ratio` style on both the grid and tray containers — this avoids either warping a mismatched image into a fixed window ratio, or needing per-tile `cover`/`contain` crop-offset math that percentage-based `background-position` slicing can't cleanly express.
- **Bundled placeholder images are a content-authoring task, not a code task** — `assets/features/jigsaw-puzzle/` needs at least a handful of varied, license-clean images before this feature is playable at all (recommend ≥6, matching Easy tier's piece count as a sane minimum pool).

**Grid tiers were retuned after playtesting**: 4×4 (16 pieces) is the *easiest* tier, scaling up to 6×5 (30 pieces) at Expert — the original 3×2→4×4 (6→16 piece) progression, which mirrored fact-sifter's own pool-size curve, played too easy at every tier. A fixed-shape rectangular-tile jigsaw is a much easier visual-matching task per piece than fact-sifter's read-and-cross-reference puzzle, so borrowing its curve undersold the difficulty. The time formula's per-piece term already scales with this automatically.

**Tray tiles must match the final grid slot's shape.** A real bug shipped in the first draft: grid slots force `width/height: 100%` (filling their CSS Grid cell), but tray tiles relied on a fixed width plus an inline `aspect-ratio` style — and Foundry's base `<button>` CSS forces an explicit `height` that silently overrides `aspect-ratio` unless countered. The grid slot's own override masked this, but tray tiles had none, so they rendered as flat wide rectangles instead of the actual (often square-ish) piece shape. Fixed with `height: auto !important` on the shared `.jigsaw-puzzle-tile` rule — same fix shape as fact-sifter's own row-height bug.

**Grid and tray are side by side, not stacked — a real "window ran full-screen tall" bug.** Once grid tiers grew to 6×5 (30 pieces) and tray tiles got big enough to actually preview, stacking grid-then-tray-then-actions vertically pushed the app window close to the player's full screen height. Fixed by laying the grid and tray out horizontally (`.jigsaw-puzzle-board`, a flex row of `.jigsaw-puzzle-grid-column` and `.jigsaw-puzzle-tray-column`) — spends the window's width instead of its height.

**Tray mirrors the grid's own `cols`/`rows`/`aspect-ratio` exactly — a real "can't see every piece without scrolling" bug.** The side-by-side fix above still had the tray flex-wrap fixed-size tiles into a scrollable column, which the player explicitly didn't want (needs to see every piece at a glance while the timer runs). Fixed by giving the tray container the identical inline `grid-template-columns`/`grid-template-rows`/`aspect-ratio` styling as the main grid (`jigsaw-puzzle-app.hbs`), guaranteeing exactly `cols × rows` (≥ `pieceCount`) cells by construction — no scrolling ever needed, and tray tiles now shrink at the same rate as the grid's own cells rather than staying a fixed pixel size. This removed the standalone `#pieceAspectRatio`/`computePieceAspectRatio` machinery entirely (sizing now comes from each tile's parent CSS Grid, same as grid slots always had). The window widened again (840 → 1000) since two equally-sized boxes side by side need more combined width than one grid alone.

See `design.md` for the DC→grid-dimensions table, the time-allowance formula and worked examples, the image pool-assembly algorithm, outcome tiers, the CSS slicing math derivation, and open implementation questions (including the still-untested drag+click coexistence).
