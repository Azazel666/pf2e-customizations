# CLAUDE.md

Guidance specific to the fact-sifter feature (see the root `CLAUDE.md` for repo-wide conventions).

## Phase 5: The Fact Sifter

An information-filtration puzzle that stands in for a flat investigation/research skill check. The GM sends a request into chat for a specific PC, DC, skill, and circumstance modifier (`pf2eCustomizations.requestFactSifter()`); any owning player can open the puzzle from the chat card (one attempt in flight at a time). A shuffled pool of short text "fragments" — a coherent chain of true facts mixed with deceptive noise (direct contradictions and irrelevant filler) — is generated fresh per attempt; pool size and noise ratio are derived from the DC alone (no secondary "clue completeness" axis, unlike timeline-puzzle/alibi-matrix — this feature's spec never asked for one, so none was invented).

- **Target files**: `scripts/features/fact-sifter/` (`fact-sifter-logic.js`, `fact-sifter-app.js` + `.hbs`, `fact-sifter-chat.js` + `-chat-card.hbs`), `scripts/macros/request-fact-sifter.js`
- **Fourth `ApplicationV2` + `HandlebarsApplicationMixin` feature**, built directly on alibi-matrix's/timeline-puzzle's *final* (already-debugged) architecture: nothing randomized is baked into the `ChatMessage` at request time — the pool is generated fresh every attempt (`generateAttempt()` in `onAttempt()`).
- **Interaction is a binary toggle** (highlight/un-highlight a fragment, not alibi-matrix's tri-state cycle or timeline-puzzle's drag-and-drop) over a single scrollable list — the simplest interaction model of the four features. Fragment rows are real `<button data-action="toggleFragment">` elements, **not** `<div>` — a deliberate choice: alibi-matrix's `<div data-action="cycleCell">` grid cells are currently reported as not responding to clicks at all (root cause still unknown), while `<button data-action>` is the most battle-tested interactive pattern in this codebase (timeline-puzzle's small move-buttons use the identical `!important`-forced-sizing approach and work correctly). Fact Sifter's rows are naturally full-width text anyway, so there was no small-fixed-size styling reason to prefer `<div>` here in the first place.
- **Outcome-on-expiration is ratio-based**, unlike either sibling (timeline uses position-count, alibi-matrix uses whole-grid-correctness): `correctSelected / selected` compared against a 50% threshold, with an explicit `selectedCount === 0` guard so "selected nothing" cleanly resolves as critical failure rather than an undefined ratio.
- **Trigger**: same pattern as the other three features — `Hooks.on('renderChatMessageHTML', ...)` renders/gates an "Attempt Sift" button based on `flags['pf2e-customizations'].factSifter` (claim/resolution state on the actor, immutable raw GM inputs on the message).

- **`FACT_CHAIN_BANK` content must follow the token-chaining authoring rule**: fact `i≥2` must verbatim-restate one specific, checkable token from fact `i-1`'s TRUE value, in all three of its own variants (true + both noise). This was a real playtest fix — the original content used implicit pronoun references ("that entry") which have no fixed antecedent once fragments are shuffled, making the puzzle unsolvable rather than just hard. See `design.md` Phase 5 "Content model" for the full rule and the incident writeup before editing or adding scenarios. Prefer short, distinctive tokens (a name, a place, a short noun phrase) over long generic clauses — easier to spot on a re-scan under time pressure.
- **Content is high-fantasy flavored, not sci-fi** — the module targets PF2e. Both scenarios were reskinned after a playtest report that the original sci-fi flavor (signal relays, credits, clerk stations) didn't fit; new scenarios should match (see `design.md` Phase 5 "Fantasy reskin"). Several UI label strings were reskinned at the same time (`verifyDataset` → "Confirm Findings", etc.) — check `lang/en.json`'s `factSifter.*` keys for current wording before adding new player-facing text.
- **Fragment row CSS must force `height`/`min-height` back to auto.** Foundry's base `button` rule sets a fixed single-line height; without overriding it, wrapped multi-line fragment text overflows silently and gets covered by the next row in the list (only the last row was ever fully readable). See `styles/features/fact-sifter.css`'s `.fact-sifter-fragment-row` comment.
- **Every scenario needs a `closingLeads` map for tiers 3/4/5 (not 6).** The token-chaining rule structurally leaves the tier's *last* included fact with zero corroboration anywhere in the pool — a real playtest transcript confirmed this is a guaranteed unsolvable coin-flip, not a minor inconvenience. `closingLeads[trueFactCount]` is a single GIVEN sentence (containing the exact excluded-link token) shown above the fragment list, never itself selectable, never counted toward `trueFactCount`. See `design.md` Phase 5 "Closing leads" before adding a scenario without one — Easy/Medium/Hard need an entry, Expert (6, the full chain) deliberately doesn't.

See `design.md` for the DC→pool-size table, the `FACT_CHAIN_BANK` content model and generation algorithm (including the leftover-pool sufficiency proof and the closing-leads mechanism), outcome tiers, and open implementation questions.
